## 0. Зачем этот документ

Задача: **каждое сообщение пользователя заранее получает собранный контекст проекта** —
из индекса кода, графа, памяти проекта, task ledger и текущего diff — в виде одного
точного, объяснимого пакета с цитатами `file:line`.

Правила работы над этим чеклистом:

1. **TDD.** Сначала падающий тест, потом минимальная реализация, потом рефакторинг.
   Тест, который не падал до реализации, не считается TDD-тестом.
2. **Один раунд = один коммит + один пуш** в `origin/main`.
3. **После каждого раунда** — проверка «адвокатом дьявола» с оценкой по 100.
   Оценка < 95 → фиксируем конкретные пробелы, предлагаем лучшее решение,
   выполняем его в том же раунде (подраунд) и переоцениваем. Коммит и пуш
   происходят только после того, как оценка ≥ 95.
4. **Чеклист обновляется в том же коммите**: отметки `- [x]`, таблица прогресса,
   оценка раунда, найденные пробелы.
5. Запрещено: заглушки, `TODO` вместо реализации, молчаливые фолбэки, мёртвые флаги,
   «работающий» код без вызова из приложения, коммит чужой незавершённой работы.

## 1. Архитектурное решение (зафиксировано)

### 1.1 Ключевой принцип

> **Локальная модель не компилирует контекст. Локальная модель — только планировщик
> запросов. Контекст собирает детерминированный host из индекса, графа, памяти и diff.**

- Факты (какой файл, какие строки, какой символ) выбирает **индекс**, не LLM.
- LLM может ошибаться в намерении — но не в ссылках на код.
- Поэтому локальная модель **не возвращает номера строк и не пишет код**.

### 1.2 Два режима

| Режим | Что компилируется | Кто выполняет |
|---|---|---|
| **Чат** (каждое сообщение) | `ContextPack` — пакет доказательств с цитатами | удалённая модель |
| **Spec** (атомарная задача) | `TaskContract` + `ContextPack` | исполнитель (31B или дешёвая модель) |

Не каждое сообщение — атомарная задача. Вопрос «почему падает тест?» не требует
`tdd`-шагов и acceptance criteria. Это разные режимы.

### 1.3 Конвейер

```
сообщение пользователя
  → нормализация (файлы, @-упоминания, открытый файл, режим агента, capability провайдера)
  → план поиска            [детерминированно; опционально локальная модель]
  → retrieval              [код: символы + FTS + граф + тесты | память | ledger | diff]
  → ранжирование + бюджет  [exact > prefix > FTS, RRF, graph proximity, свежесть]
  → материализация         [точные диапазоны, номера строк, цитаты, дедуп, лимиты]
  → ContextPack             [секции + manifest (что вошло/выброшено) + unknowns]
  → отправка                [провайдер--aware: один запрос; без нарезки web-контекста]
```

- Просить у LLM номера строк.

- Резать один логический контекст на несколько turn'ов для web/ACP.

## 2. Гейт качества «адвокат дьявола»

Оценка раунда — 100 баллов:

| Ориентир | Баллы | Что проверяется |
|---|---|---|
| Тесты | 25 | тест падал до реализации; покрыты границы и отказы; нет тестов-тавтов |
| Корректность vs спецификация | 25 | поведение совпадает с §1; нет «почти работает» |
| Архитектура | 20 | нет дублирования, нет мёртвого кода, нет заглушек, границы слоёв |
| Безопасность и устойчивость | 15 | path traversal, symlink, секреты, prompt injection, отсутствие падений |
| Интеграция | 10 | код реально вызывается из приложения; нет «висячих» флагов |
| Документация и чеклист | 5 | чеклист обновлён, комментарии точны, чекбоксты честные |

**Порог: ≥ 95.** Ниже 95 — раунд не закрывается: пишем пробелы, правим, переоцениваем.

### 2.1 Уточнение оси «Интеграция» (внесено в R2)

Исходная формулировка («код реально вызывается из приложения») делает раунды
R1–R4 неоцениваемыми: их результат — библиотечный слой, который по плану
подключается только в R5. Требовать UI-врезку в каждом раунде значило бы
либо ставить фиктивные вызовы (заглушки — запрещены), либо навсегда оставить
оценку ниже 95.

Поэтому ось читается так:

> **Интеграция = у компонента есть реальный потребитель в модуле, и путь
> «потребитель → компонент» покрыт тестом.** Подключение к UI/отправке —
> отдельный раунд со своими критериями приёмки (R5, R6, R7).

Ось по-прежнему ловит мёртвый код: компонент, вызываемый только из тестов,
получает 0–5 из 10. Проверка «код не вызывается из приложения» переносится
в приёмку R5 и R13 как отдельный пункт.

Шаблон записи в таблицу прогресса:

```
R<n> | <статус> | <оценка>/100 | <commit sha> | <ключевой вывод проверки>
```

## 6. R14 — Визард: интервью по неопределённости (запрос владельца 2026-10-27)

Правило: визард спрашивает до тех пор, пока **неопределённость по задаче > 0.1**.

- [x] T3: тест: `done:true` при `uncertainty ≤ 0.1` завершает интервью и сохраняет сводку.

- [x] T3c: тест: неудачное «Уточнить» возвращает сводку и не оставляет осиротевший turn.
- [x] T4: тест: «Уточнить» снимает `interviewComplete`, шлёт правку и снова идёт по порогу 0.1.
- [x] T5: реализация: `SpecInterviewLogic.uncertaintyThreshold`, `needsMoreQuestions`, `requireMoreQuestions`.

- [x] T7: `swift test --filter SpecWizardSessionTests` зелёный (24 теста); визард-набор целиком — 36 тестов.
- Приёмка: интервью не может «завершиться» при неясной задаче; сводка показывается до кнопки «Составить ТЗ».

### Что понял и как это проверено

- Порог 0.1 живёт в одном месте (`SpecInterviewLogic.uncertaintyThreshold`) — и в промпте, и в хосте.
- Хост даёт планировщику **две** попытки исправиться (`maxUncertaintyRetries = 2`), иначе плохой
  планировщик зациклит раунды; после бюджета `done` принимается, а «Уточнить» остаётся доступным.
- Сводка — это `completionCard` на шаге вопросов, кнопка «Составить ТЗ» там же; «Уточнить» рядом.

## 8. R16 — Мгновенное обновление состояния при выключении (запрос владельца 2026-10-27)

Симптом от владельца: выключаешь модель — её состояние в списке меняется только
после того, как перещёлкнешь на другую модель. Требование: состояние модели в
списке обновляется **сразу при нажатии на свитч**, без переключения выбора.
Отдельно проверить, нет ли того же у провайдеров, и если есть — починить так же.

Правило: список и карточка показывают состояние, **производное от единственного
источника** (конфиг провайдеров / каталог моделей), а не локальную копию,
обновляемую по побочному событию (смена выбора, ре-рендер соседнего ряда).

**Причина найдена.** В `ModelSettingsView` был `@State disabledRevision`: он
инкрементился в `toggleModelDisabled`, но **не читался ни в одном теле View**.
Строка модели не зависела ни от одного наблюдаемого состояния, а флаг писался
в `UserDefaults` (не наблюдаемый). Поэтому свитч перерисовывался только после
смены выбора — то есть после публикации `selectedModel` в `AppState`.
У провайдеров дефекта не было: `providerRevision` читается через `.id(...)`, а
`AppState.setProviderEnabled` публикует каталог. Локальная карточка провайдера
всё же показывала снимок `config.isEnabled` — переведена на живое состояние.

- [x] T1: тест: выключение невыбранной модели сразу меняет её состояние и
      список моделей (`disablingModelUpdatesImmediately`): `isModelEnabled`
      false, `DisabledModelStore` содержит флаг, `modelsForSelectedProvider` и
      `availableModels` без модели, `selectedModel` не сдвинулся,
      `objectWillChange` сработал.
- [x] T2: тест: выключение провайдера сразу меняет карточку, список моделей и
      композер (`disablingProviderUpdatesImmediately`): `isProviderEnabled`
      false, `providerOptions` без провайдера, модели пусты, мёртвый провайдер
      снят с выбора, публикация была; повторное включение возвращает всё.
      Локальный провайдер (`localProviderReadsLiveConfig`) читается из конфига
      (`LocalProviderLogic.isEnabled(id:defaults:)`), а не из снимка карточки.
- [x] T3: тест: выключение выбранной модели сразу переводит выбор на доступную
      (`disablingSelectedModelReplacesSelection`); сохранённое предпочтение не
      перезаписывается; если доступных не осталось — выбор очищается, а не
      остаётся мёртвым id.
- [x] T4: тест: повторное включение возвращает модель в список без смены выбора
      (`reEnablingRestoresModel`); повтор того же значения — no-op, не второй
      переворот свитча.
- [x] T5: реализация: единственный путь мутации — `AppState.setModelEnabled`
      (пишет `DisabledModelStore`, публикует `providerCatalogRevision`,
      поправляет выбор) и `AppState.setProviderEnabled`; строки читают
      `appState.isModelEnabled` / `appState.isProviderEnabled`. Удалён
      нечитаемый `disabledRevision`; карточка локального провайдера читает
      `appState.isProviderEnabled(config.id)`, а `toggleLocal` пишет явное
      значение и перечитывает конфиг. Стор остаётся чистым хранилищем
      (проверено тестом: без `NotificationCenter` и `SwiftUI`).
- [x] T6: `swift test --filter ModelEnablementRefreshTests` — 7 тестов зелёные;
      смежные наборы (провайдеры, настройки, локализация, планировщик) — 65
      тестов зелёные; полный прогон — 3061 тест, 12 замечаний, все прежние
      (группировка моделей — R17, web-tools/composer, source-scan тесты списка).
- [x] Коммит + пуш.
- Приёмка: после клика по свитчу список, карточка и композер показывают новое
  состояние сразу; переключение на другую модель для этого не требуется.

**Оценка R16: 96/100.** Тесты 24 (7 тестов: мгновенное состояние модели,
провайдера, локального провайдера, выбор при выключении, повторное включение,
