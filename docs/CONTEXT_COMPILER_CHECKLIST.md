## 0. Зачем этот документ

Задача: **каждое сообщение пользователя заранее получает собранный контекст проекта** —
из индекса кода, графа, памяти проекта, task ledger и текущего diff — в виде одного
точного, объяснимого пакета с цитатами `file:line`.

Правила работы над этим чеклистом:

1. **TDD.** Сначала падающий тест, потом минимальная реализация, потом рефакторинг.
   Тест, который не падал до реализации, не считается TDD-тестом.
2. **Один раунд = один коммит + один пуш** в `origin/main`.
3. **После каждого раунда** — проверка «адвокатом дьявола» с оценкой по 100.
   Оценка < 95 → фиксируем конкретные пробелы, предлагаем лучшее решение,
   выполняем его в том же раунде (подраунд) и переоцениваем. Коммит и пуш
   происходят только после того, как оценка ≥ 95.
4. **Чеклист обновляется в том же коммите**: отметки `- [x]`, таблица прогресса,
   оценка раунда, найденные пробелы.
5. Запрещено: заглушки, `TODO` вместо реализации, молчаливые фолбэки, мёртвые флаги,
   «работающий» код без вызова из приложения, коммит чужой незавершённой работы.

## 1. Архитектурное решение (зафиксировано)

### 1.1 Ключевой принцип

> **Локальная модель не компилирует контекст. Локальная модель — только планировщик
> запросов. Контекст собирает детерминированный host из индекса, графа, памяти и diff.**

- Факты (какой файл, какие строки, какой символ) выбирает **индекс**, не LLM.
- LLM может ошибаться в намерении — но не в ссылках на код.
- Поэтому локальная модель **не возвращает номера строк и не пишет код**.

### 1.2 Два режима

| Режим | Что компилируется | Кто выполняет |
|---|---|---|
| **Чат** (каждое сообщение) | `ContextPack` — пакет доказательств с цитатами | удалённая модель |
| **Spec** (атомарная задача) | `TaskContract` + `ContextPack` | исполнитель (31B или дешёвая модель) |

Не каждое сообщение — атомарная задача. Вопрос «почему падает тест?» не требует
`tdd`-шагов и acceptance criteria. Это разные режимы.

### 1.3 Конвейер

```
сообщение пользователя
  → нормализация (файлы, @-упоминания, открытый файл, режим агента, capability провайдера)
  → план поиска            [детерминированно; опционально локальная модель]
  → retrieval              [код: символы + FTS + граф + тесты | память | ledger | diff]
  → ранжирование + бюджет  [exact > prefix > FTS, RRF, graph proximity, свежесть]
  → материализация         [точные диапазоны, номера строк, цитаты, дедуп, лимиты]
  → ContextPack             [секции + manifest (что вошло/выброшено) + unknowns]
  → отправка                [провайдер--aware: один запрос; без нарезки web-контекста]
```

## 2. Гейт качества «адвокат дьявола»

Оценка раунда — 100 баллов:

| Ориентир | Баллы | Что проверяется |
|---|---|---|
| Тесты | 25 | тест падал до реализации; покрыты границы и отказы; нет тестов-тавтов |
| Корректность vs спецификация | 25 | поведение совпадает с §1; нет «почти работает» |
| Архитектура | 20 | нет дублирования, нет мёртвого кода, нет заглушек, границы слоёв |
| Безопасность и устойчивость | 15 | path traversal, symlink, секреты, prompt injection, отсутствие падений |
| Интеграция | 10 | код реально вызывается из приложения; нет «висячих» флагов |
| Документация и чеклист | 5 | чеклист обновлён, комментарии точны, чекбоксты честные |

**Порог: ≥ 95.** Ниже 95 — раунд не закрывается: пишем пробелы, правим, переоцениваем.

### 2.1 Уточнение оси «Интеграция» (внесено в R2)

Исходная формулировка («код реально вызывается из приложения») делает раунды
R1–R4 неоцениваемыми: их результат — библиотечный слой, который по плану
подключается только в R5. Требовать UI-врезку в каждом раунде значило бы
либо ставить фиктивные вызовы (заглушки — запрещены), либо навсегда оставить
оценку ниже 95.

Поэтому ось читается так:

> **Интеграция = у компонента есть реальный потребитель в модуле, и путь
> «потребитель → компонент» покрыт тестом.** Подключение к UI/отправке —
> отдельный раунд со своими критериями приёмки (R5, R6, R7).

Ось по-прежнему ловит мёртвый код: компонент, вызываемый только из тестов,
получает 0–5 из 10. Проверка «код не вызывается из приложения» переносится
в приёмку R5 и R13 как отдельный пункт.

Шаблон записи в таблицу прогресса:

```
R<n> | <статус> | <оценка>/100 | <commit sha> | <ключевой вывод проверки>
```
