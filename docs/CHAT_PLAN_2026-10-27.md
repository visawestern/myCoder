## 7. Решение «адвоката дьявола»: когда обновлять индекс кода

Вариант «полный ре-индекс перед каждым сообщением» отклонён:
на проекте такого размера это единицы секунд на сообщение, и всё это время
пользователь ждёт; выигрыш нулевой, потому что между двумя сообщениями
файлы меняет в основном сам агент — а он и так знает, что изменил.

Принято: **динамически, по факту изменения**.
1. Watcher помечает изменившиеся файлы (уже есть).
2. Перед сборкой контекста пересчитываются только помеченные файлы (инкрементально).
3. `edit_file`/`write_file` сами инвалидируют запись файла сразу после записи,
   поэтому следующий `read_file`/`grep` видит актуальное содержимое.
4. Если файл изменился вне приложения и watcher не успел — `edit_file`
   падает с «text not found» и просит перечитать файл; это дешёвый и явный
   сигнал вместо устаревшей правки.

## 10. Аудит «адвоката дьявола» (2026-10-27, второй проход)

Что было реально сломано и исправлено **до** коммита:

1. **Дубли ответа.** Ответ писался в БД *до* запроса к планировщику. Планировщик падал →
   ответ уже в ленте, карточка вопроса возвращалась, повторный ответ писал второй такой же
   turn. Теперь ответ и вопрос пишутся одной транзакцией успеха; при сбое не пишется ничего
   (`failedAnswerKeepsQuestionCardVisible` проверяет отсутствие дубля).
2. **Потеря сводки при сбое «Уточнить».** `clarify` снимал `interviewComplete` и чистил
   сводку до запроса; при ошибке пользователь оставался на пустом экране вопросов.
   Теперь состояние восстанавливается (`failedClarificationKeepsSummary`).
3. **Регрессия парсера.** Гейт `calls.isEmpty && issues.isEmpty` не давал спарсить валидный
   unfenced-вызов, если рядом был битый fenced-блок. Гейт ослаблен до `calls.isEmpty`
   (`brokenFencedBlockDoesNotHideUnfencedCall`).
4. **Вечный спиннер.** Пустая лента всегда показывала «Готовим первый вопрос…», даже когда
   запрос уже упал (ровно это и выглядело как «всё зависло» на скриншоте). Теперь спиннер
   только при реальном запросе, иначе — честный текст + «Повторить».
5. **Лимит неопределённости был 1 повтор** — не соответствовал правилу «спрашивай, пока
   > 0.1». Стало 2 повтора с жёстким бюджетом, чтобы плохой планировщик не зациклил раунды.
6. **Гонка двойной отправки.** Возврат текста в поле теперь только при реальной ошибке,
   а не когда сессия ещё занята.
7. **API отдавал не тот шаг.** `wizardState` теперь отдаёт `visibleStep` и `activeStep`
   рядом с `step` (сколько проект прошёл).

Остаточные риски, которые приняты осознанно:

- После исчерпания бюджета повторов «упрямый» `done` при uncertainty 0.4 принимается —
  альтернатива (бесконечные повторы) хуже; пользователь видит сводку и может нажать «Уточнить».
- Буфер редактора ТЗ не автосохраняется (ревизия создаётся кнопкой) — см. §9.

## 14. Запрос пользователя 2026-10-29, раунд 4: фоновый стриминг и индикатор в списке чатов

**Запрос.** Если модель умеет стримить, текст должен приходить в фоне: можно
переключиться на любой другой чат и не прерывать текущий ответ. В списке чатов
должен быть виден прогресс — бегущая полоса под строкой или круговой лоадер
перед названием чата, пока идёт общение с моделью.

**Причина, по которой фон не работал (по коду, не по догадке).**

1. `MessageStore` держал **один** массив `messages`. `loadSessionMessages`
   вызывал `clear()` при каждом переключении чата, то есть стирал ленту, в
   которую писал незавершённый ход.
2. `handleSSEEvent` начинался с `if sessionID != messageStore.currentSessionID { return }`.
   После переключения чата все события продолжающегося хода отбрасывались:
   текст молча терялся, сообщение навсегда оставалось «стримящимся».
3. `SessionReloadLogic` не перезагружал историю, пока `appState.isLoading`
   (глобальный флаг любого хода). Из-за этого при переключении во время ответа
   под новым заголовком показывались сообщения предыдущего чата.
4. Отправка читала `messageStore.currentSessionID` после каждого `await`
   (создание сессии, компиляция контекста, история, вложения). Переключение в
   этот момент уводило пользовательское сообщение, ответ и запись в БД в чужой чат.

**Что сделано.**

- `MessageStore` хранит **ленту на сессию** (`feeds: [String: SessionFeed]`):
  `messages(in:)`, `message(id:)`, `sessionID(owningMessageID:)`,
  `hasLoadedMessages(sessionID:)`, `append(_:to:)`. Все записи стрима идут по
  id сообщения, поэтому чанк, пришедший после переключения, попадает в свою
  ленту и сохраняется в БД своей сессии.
- `detach()` заменяет `clear()` при смене чата: видимая лента отвязывается,
  остальные (включая активные) остаются в памяти. `clear()` оставлен только
  для полного сброса/тестов.
- Повторное открытие уже загруженного чата не перечитывает историю
  (`SessionReloadLogic.shouldReloadMessages(hasCachedMessages:)`), поэтому
  возврат в стримящийся чат показывает уже пришедшие чанки, а не откат к БД.
  `loadFromDatabase` при непустой ленте сливает строки по id и не затирает
  сообщение, у которого `isStreaming == true`.
- Ход фиксирует `turnSessionID`/`sendSessionID` до первого `await`; все
  `append`, история для модели, вложения, ledger, Git-refresh, уведомление о
  завершении и `abortSession` используют его, а не видимый чат. Очередь
  сообщений (`QueuedMessage.sessionID`) помнит чат, в котором сообщение
  поставлено в очередь.
- `handleSSEEvent` принимает события сессии, которой принадлежит текущий
  assistant-ход (плюс видимой), и отбрасывает посторонние. `finishStreaming`
  и `stopGeneration` определяют сессию по id сообщения; вопрос плана
  (`pendingQuestionRequest`) привязан к своей сессии — карточка показывается
  только в ней и не блокирует завершение чужого хода.
- `AppState.streamingSessionIDs` — набор чатов с живым ходом (стрим или
  ожидание ответа на вопрос). `ChatPanelView` синхронизирует его из
  `MessageStore`; `SidebarView` показывает `BackgroundActivityIndicator`
  (круговой лоадер) перед названием такого чата и в project-less строке.
- Composer показывает Stop только для видимого стримящегося чата; отправка в
  другом чате по-прежнему встаёт в очередь (одновременно выполняется один ход),
  но теперь очередь доставляет её в исходный чат.
