### 0.2 Почему задумка владельца не видна в работе

1. **Всё уже написано, но не сдано.** Реализация п.1–3 лежит **незакоммиченной**
   в рабочем дереве (29 файлов, +951/−2184 — вперемешку с браузерным агентом,
   который удалил WKWebView-мост). Установленный `.app` (v2.119.15, сборка
   2026-11-02) собран **до** этих правок — владелец проверяет старый бинарь и
   закономерно видит, что «задумка не работает». Root-cause №1.
2. **Внутренняя модель по умолчанию выключена.** `LocalPlannerSettings.defaultEnabled == false`
   → `isLocalQueryPlannerEnabled = false` → `InternalContextPlanner` не вызывается
   вовсе. Плюс `InternalModelStore` пуст, пока владелец не назначил модели
   «внутренними». В пакете это проявляется как «детерминированный план».
   Архитектура (host собирает факты, внутренняя модель — только планировщик,
   `CONTEXT_COMPILER_CHECKLIST.md` §1.1) правильная и сохраняется, но
   **участие внутренней модели должно быть состоянием по умолчанию**, как в
   задумке. Root-cause №2.
3. **Лог сборки не показывает граф и скиллы.** В `sendDirectly` проставляются
   стадии `.index`, `.memory`, `.planning`, `.files` и финал; стадии `.graph`
   и `.skills` из `ContextStageLogLogic.Stage` существуют, но не эмитятся —
   граф/скиллы собираются внутри `TurnContextCompiler.compile` без обратного
   вызова. Пункт 2 запроса выполнен наполовину. Root-cause №3.
4. **Харнесс не задаёт вспомогательные вопросы о зависимостях.** Секция
   «Граф кода» перечисляет соседей символа, но ничто не заставляет модель
   **пройти по каждой связи и решить её судьбу** (пример владельца: хранение
   кадров переехало из файлов в память → раздел выбора папки в UI стал мёртвым,
   но модель сама об этом не спросит). Root-cause №4 — это новый раунд C5.

Замечания по гигиене (чинить в C1):
- `ChatPanelView:1670–1674`: комментарий «первый промпт не собирает контекст»

- `SendContextStatus.firstTurn` сейчас достижим только для чата без проекта —

## 3. Поток C — харнесс-вопросы о зависимостях (C5, новый)

Задумка владельца (дословно из запроса 2026-11-03): харнесс при создании
контекста задаёт правильные дополнительные вопросы, которые говорят модели о
правильном порядке изменения кода: отработать каждую связь и зависимость,
проверить и решить, что с ними делать. Пример: хранение кадров переехало из
файлов в память → раздел выбора папки в UI больше не нужен, и модель должна
сама это вывести из графа, а не только править запрошенную функцию.

Архитектура — как у всего конвейера: **детерминированный хост поверх графа,
внутренняя модель только обогащает** (опционально, помечено источником).

### 3.1 Дизайн

Новый тип `ImpactAnalyzer` (чистый, детерминированный, тестируемый):

```
ImpactAnalyzer.analyze(message, plan, graph, index) -> ImpactReport
ImpactReport {
  affectedSymbols: [Symbol]        // символы запроса, найденные в графе
  dependents:  [DependencyEdge]    // ОБРАТНЫЕ рёбра: кто зовёт/тестирует/содержит (глубина ≤ 2)
  fates:       [FateQuestion]      // «решить судьбу» для каждой связи
  order:       [String]            // порядок изменений (ядро → зависимости → мёртвый код → тесты)
  questions:   [String]            // вспомогательные вопросы харнесса
  refs:        [TaskReference]     // материализовать код зависимостей как evidence
}
```

Триггер (без модели): намерение из локального плана (`refactor`/`remove`) или
ключевые слова запроса («удали/убери/замени/переделай/перенеси/больше не
нужен/remove/replace/migrate/deprecate/refactor»). Триггер не сработал — секции
нет, как у всех источников пакета.

Обязательное содержание секции «Вопросы харнесса о зависимостях»:
1. **Список связей с судьбой.** Для каждой обратной связи: `путь:строки —
   обновить / удалить / оставить — реши явно, «оставить как есть» тоже решение`.
2. **Порядок изменений.** Сначала ядро (само хранилище), потом каждый
   потребитель, потом удаление мёртвого кода (включая UI-разделы, которые
   стали не нужны), прогон тестов между шагами.
3. **Вспомогательные вопросы** (генерируются из графа, не из воздуха):
   - «какие разделы UI/настроек/документации ссылаются на удаляемый механизм и
     стали не нужны?» (поиск ссылок на символ вне его файла — через индекс);
   - «какие тесты покрывают изменяемое и как должны измениться?» (рёбра `tests`);
   - «что произойдёт с потребителями данных/формата при смене способа
     хранения?» (рёбра `calls` + `imports`).
4. **Evidence зависимостей:** код каждой связи материализуется отдельными
   блоками `file:line` (те же `ContextMaterializer`-правила: только
   project-relative, дедуп, бюджет).
