## Раунд 1 (завершён ✅): дедупликация собранного контекста

### Что проверено
- `ContextDeduplication.deduplicate` вызывается в `TurnContextCompiler.compile`
  перед финальным `render` — т.е. дедуп применяется к итоговому пакету,
  который уходит модели (путь: `SendContextPreparationLogic.prepare` →
  `TurnContextCompiler.compile` → `ContextDeduplication`).
- Покрытие тестами (17 тестов: 13 юнит + 4 интеграционных) подтверждает:
  - один блок на файл (кандидат + «— зависимость» одного пути);
  - точный повтор содержимого;
  - строки из файловых блоков не повторяются в истории/памяти;
  - «Запрос» пользователя неприкосновенен;
  - разные файлы с общим boilerplate остаются оба;
  - смысловой дубль (Jaccard ≥0.85 / вхождение) в повествовательных секциях;
  - порядок секций после дедупа сохраняется.

### Найденные и исправленные дефекты
1. **Cтроки с номерами не дедуплицировались.** `ContextMaterializer` рендерит
   код как `42 | let x = …`, а диалог цитирует ту же строку без номера.
   Фильтр «строк из файлов» не находил совпадений → дубль «из диалога и из
   файлов» оставался. Исправлено: `ContextDeduplication.stripLineNumberPrefix`
   снимает префикс `N | ` и запоминает обе формы.
   Тесты: `numberedFileLinesMatchNarrative`, `fullyRedundantNarrativeDropped`
   (были красные → стали зелёные).
2. **Цитаты выброшенных секций оставались в пакете.** После дедупа фильтр
   был только по пути, поэтому цитата секции «path — зависимость» (отброшена
   как дубль файла) выживала. Исправлено: цитаты сверяются с заголовками
   реально включённых блоков (`keptBlockHeaders`).
   Тест: `candidateAndDependencySameFileSingleBlock`.

### Регрессия
- Полный прогон: 3750 тестов, падают только 2 Git-теста по таймауту
  («Git command timed out») — воспроизводятся и на чистом HEAD (флаки
  окружения, не связаны с изменениями).

- [x] **C1. Статус сборки контекста не привязан к chatId.** Строка статуса
  сборки контекста показывается не в том чате, где запущена.

- [x] **C2. Цель (goal) не привязана к чату** в строке состояния и под ней.
  Сделано (2026-11-10, TDD: `ContextSessionStatusLogicTests`).

- [x] **C6. Размер контекста чата не пересчитывается сразу после смены
  модели/параметров** (следующее сообщение уходит со старым размером).
  Сделано (2026-11-10, TDD: `ContextBudgetLogicTests`, 8 тестов).
  Найдены и исправлены три причины:

- [ ] **P1. Системный промпт по режиму работы и живой каталог инструментов.**
  Проверить и при необходимости переработать промпт для Build/Plan/Compose,
  как это делает OpenCode: при смене режима, доступных инструментов и скиллов
  в чате добавлять точное описание того, что реально доступно и как этим
  пользоваться, а не один статический список.

  Анализ текущего состояния (2026-11-10): режимы уже различаются —
  `TurnDelivery.systemInstruction` → `PlanModePromptBuilder.resolve`
  (`Build` без напоминания, `Plan` read-only + todo-план, `Compose`
  read-only для текстов). Текстовые transport-ы получают полный/профильный
  список `WebEmulatedTool`; native transport доверяет runtime-схемам.
  Слабые места, которые нужно закрыть: профиль и фактические доступные тулы
  не сверены в одном контракте на всех маршрутах; нет единого правила
  обновления описания после изменения доступности/MCP/скиллов; план-напоминание
  добавляется поверх общего промпта, а не заменяет противоречащие инструкции.

  Адвокат дьявола: не копировать огромный каталог OpenCode дословно — это
  раздувает контекст и может обещать инструменты, которых у провайдера нет;
  не скрывать изменения доступности только в UI — модель должна получить
  новый контракт на следующем ходе. Лучшее решение: единый генератор
  `ToolInstructionGuide`/`systemPreamble` с явным входом режима, профиля,
  фактически доступных тулов и установленных скиллов; детерминированная
  ревизия каталога; короткое описание core + on-request схемы; native-текст
  не должен утверждать, что текстовые fences исполняются. TDD: тесты на
  различие Build/Plan/Compose, исключение недоступных тулов, изменение
  каталога между ходами и отсутствие ложных обещаний; затем живой прогон
  переключения режима и отправки.
