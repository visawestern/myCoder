## Раунд 1 (завершён ✅): дедупликация собранного контекста

### Что проверено
- `ContextDeduplication.deduplicate` вызывается в `TurnContextCompiler.compile`
  перед финальным `render` — т.е. дедуп применяется к итоговому пакету,
  который уходит модели (путь: `SendContextPreparationLogic.prepare` →
  `TurnContextCompiler.compile` → `ContextDeduplication`).
- Покрытие тестами (17 тестов: 13 юнит + 4 интеграционных) подтверждает:
  - один блок на файл (кандидат + «— зависимость» одного пути);
  - точный повтор содержимого;
  - строки из файловых блоков не повторяются в истории/памяти;
  - «Запрос» пользователя неприкосновенен;
  - разные файлы с общим boilerplate остаются оба;
  - смысловой дубль (Jaccard ≥0.85 / вхождение) в повествовательных секциях;
  - порядок секций после дедупа сохраняется.

### Найденные и исправленные дефекты
1. **Cтроки с номерами не дедуплицировались.** `ContextMaterializer` рендерит
   код как `42 | let x = …`, а диалог цитирует ту же строку без номера.
   Фильтр «строк из файлов» не находил совпадений → дубль «из диалога и из
   файлов» оставался. Исправлено: `ContextDeduplication.stripLineNumberPrefix`
   снимает префикс `N | ` и запоминает обе формы.
   Тесты: `numberedFileLinesMatchNarrative`, `fullyRedundantNarrativeDropped`
   (были красные → стали зелёные).
2. **Цитаты выброшенных секций оставались в пакете.** После дедупа фильтр
   был только по пути, поэтому цитата секции «path — зависимость» (отброшена
   как дубль файла) выживала. Исправлено: цитаты сверяются с заголовками
   реально включённых блоков (`keptBlockHeaders`).
   Тест: `candidateAndDependencySameFileSingleBlock`.

- [x] **M1. Маршрутизатор моделей в панели ввода: единая модель или отдельные
  провайдеры/модели для каждого типа работы.**
  Добавить в композер новый кастомный селект рядом с текущими выборами
  провайдера/модели. В простом режиме — «Одна модель для всего»: существующий
  выбор остаётся единственным источником для всех шагов. В расширенном —
  «По типам действий»: для каждой роли независимо выбираются провайдер, модель
  и при необходимости effort/параметры. Переключение режима не должно молча
  терять индивидуальные назначения; при возврате к единой модели они
  сохраняются как неактивная конфигурация.

  **UX и область настроек.** Селект показывает текущее состояние коротко:
  «Единая: provider/model» либо «Маршруты: N». Раскрытие даёт список ролей с
  provider → model, capability-индикаторами (текст/vision/tools), кнопками
  «Применить ко всем», «Сбросить к единой» и явным предпросмотром цепочки.
  Настройки по умолчанию — на проект, с возможным override на чат; выбранная
  конфигурация сохраняется и показывается до отправки. Недоступный провайдер,
  удалённая модель или отсутствие credentials видны заранее; нельзя молча
  отправить запрос другому провайдеру.

  **Минимальный набор независимых ролей (не дробить каждый тул искусственно):**
  1. **Классификация/диспетчеризация запроса** — определяет нужные ветки
     (код, план, текст, изображение, web), но не выполняет работу.
  2. **Планирование и декомпозиция** — строит план, критерии приёмки и
     зависимости; результат в структурированном формате передаётся дальше.
  3. **Исследование контекста** — чтение файлов/графа/поиска и сбор evidence;
     отдельно от финального письма, чтобы можно было назначить дешёвую модель.
  4. **Основное исполнение** — код/правки/текст ответа и вызовы инструментов;
     получает план и evidence предыдущих ролей, а не только сырые логи.
  5. **Проверка и ревью** — независимый разбор diff/тестов/рисков; может
     использовать другого провайдера, чтобы не повторять слепые пятна автора.
  6. **Исправление по результатам проверки** — отдельный вызов исполнителя
     только при найденных ошибках, затем повторная проверка с лимитом циклов.
  7. **Сжатие/резюме и handoff между ходами** — история, tool-результаты,
     compaction и перенос контекста при смене модели/провайдера.
  8. **Vision/OCR** — анализ скриншотов и изображений, включая извлечение
     текста, UI-элементов и структуры для последующих текстовых моделей.
  9. **Финальная сборка ответа пользователю** — необязательная роль: объединяет
     результаты веток без выдумывания невыполненных действий.

  **Цепочка исполнения — направленный граф с условными ветками, а не всегда
  фиксированный конвейер.** Базовый кодовый путь: диспетчер → планирование →
  исследование → исполнение → тесты/ревью → (исправление → повторная проверка)
  → финальный ответ. Плановый путь заканчивается согласованным планом и не
  запускает исполнение до смены режима/явного разрешения. Compose минует
  кодовое исполнение. Если есть изображения, vision-роль выполняется до
  диспетчера/планировщика либо параллельно независимым веткам; её структурный
  результат передаётся текстовым моделям. Независимые исследования могут идти
  параллельно, зависимые шаги ждут реальные результаты; у циклов ревью и
  повторов есть жёсткий лимит, отмена и видимый статус каждой роли.

  **Vision-fallback — обязательный сценарий.** Если у основной модели нет
  поддержки изображений, вложение автоматически направляется назначенной
  vision-модели; основная получает только фактическое описание/OCR и ссылку
  на исходное вложение. Если vision-модель не назначена или недоступна,
  отправка не должна притворяться успешной: показать ошибку и предложить выбор.
  Capability определяется реальным каталогом/контрактом провайдера, а не
  эвристикой по названию модели; ошибки распознавания не подменяются выдумкой.

  **Единый контракт маршрутизации.** Ввести чистые модели `ModelRole`,
  `ModelAssignment(providerID, modelID, parameters)`, `ModelRoutingConfiguration`
  и план `TurnRouteGraph`; resolver возвращает фактический provider/model для
  каждого узла. Все отправки (обычный чат, goal/autonomous loop, subagents,
  compaction, planner, vision) должны проходить через него — иначе UI будет
  обещать маршрут, которого нет. Каждый узел сохраняет sessionID, role,
  provider/model, входные артефакты, usage, ошибку и результат; панель показывает
  реально исполненную цепочку. Явно запретить скрытый cross-provider fallback:
  retry/fallback только из заранее показанного правила и с записью в журнал.

  **Границы и безопасность.** Учитывать стоимость, задержку, лимиты и передачу
  кода/изображений разным внешним провайдерам; перед первым cross-provider
  маршрутом показать понятное предупреждение. Локальные/веб/native transport-ы
  не смешивать неявно. Credentials остаются в существующем защищённом хранилище,
  в логах — только идентификаторы. Отмена родительского хода отменяет все
  дочерние запросы; переключение чата не переносит чужие результаты.

  chat/project precedence, удалённая модель, отсутствие vision/tools), затем
